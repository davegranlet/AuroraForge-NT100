# Publishing rules

GitHub is the canonical and preferred publication channel for Aurora Forge NT100. These rules apply to every release unless the owner explicitly changes them.

## Canonical location

- Source code lives in `davegranlet/AuroraForge-NT100` on GitHub.
- Every downloadable release artifact is attached to a GitHub Release on that repository. This includes Windows installers, block maps, `latest.yml`, Linux archives, source ZIPs, and checksum files.
- The website `auroraforge.live` is the public front door and may mirror or link release downloads. It is not the release authority. Mirrors must match the GitHub asset names and SHA-256 hashes.
- Do not move release artifacts to self-hosting, third-party file hosts, or a generic updater feed without an explicit owner decision.

## Repository contents

- The repository contains source, tests, build scripts, public documentation, and notices only.
- Never commit installers, ZIPs, archives, block maps, game data, generated outputs, decompiled code, private research, secrets, or local state.
- Keep `.gitignore` current for build outputs, large evidence trees, generated tool libraries, and private data.
- Review `git status` and the staged file list before every commit. Never use a blind `git add -A`.
- Aurora Forge source is GPL-3.0-or-later. Third-party components keep their own licenses and notices.

## Release assets

Each release must publish, at minimum:

- Windows NSIS installer and `.blockmap`
- `latest.yml` generated by electron-builder
- Linux x64 archive
- `SHA256SUMS.txt`
- Source ZIPs when source downloads are part of the release

Keep asset names stable and versioned. Upload artifacts with `gh release upload` or electron-builder's GitHub publisher. Do not hand-edit `latest.yml`.

If GitHub asset limits are reached, split large archives into parts on the same GitHub Release or ask the owner for a decision. Do not silently move the canonical release elsewhere.

## Auto-updates

- The app uses electron-builder's GitHub provider and the repository's GitHub Releases as its update feed.
- Keep `publish.provider: github` with owner `davegranlet` and repo `AuroraForge-NT100`.
- Never point the updater at the website or a self-hosted `latest.yml`.

## Release checklist

1. Bump the version in the app package, app config, manifest, website, release notes, and version history.
2. Stage source-only changes and confirm no generated, private, binary, or oversized files are included.
3. Run the source tests and app verification.
4. Build the Windows installer and Linux archive. On Windows, use `npm run dist:win` and the Linux packager fallback.
5. Confirm the package contains no retired gated converter preview and no protected entitlement payloads.
6. Commit and push the source.
7. Create the `vX.Y.Z` GitHub Release and attach every release asset.
8. Point the website at the GitHub Release assets or upload matching mirrors, then verify the SHA-256 values.
9. Verify the updater metadata and the release asset list.

Do not force-push, rewrite published tags, or remove assets from a published release without owner approval.
